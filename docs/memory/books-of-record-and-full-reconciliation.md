**Decided by the user (2026-10-05):** (1) party-wise accounting: suppliers and customers become ledgers under Sundry Creditors/Debtors, with Purchase and Sales vouchers, bill references and bill-wise settlement of bank lines, TDS at payment, advances as party balances. (2) AutoCA is the FINAL books of record, not a feeder for Tally, so reports, sign-off and checks must be complete and audit-ready. (3) Scope is "cover everything" a CA firm receives; no single priority. Full design: `docs/design/party-accounting-phase1.md`. The user never answered the TDS-timing question (#3 in the design), so 1a uses the recommended default (deduct at booking, typed by the CA) which is easy to change.

**Why:** before this, bank lines posted straight to expense heads: no creditor/debtor balances, no outstanding bills, no GST input from invoices, and `gst/` was an island. See [[feedback-no-islands-reconcile-everything]].

**Target model:** one ledger at the centre; every document is a source of entries or evidence; each type proves itself; each reconciles to a control account; anything unmatched is an open item (one computed list, `ledger/openitems.py`, detectors registered per module); sign-off will be gated on it.

**Step 1a and 1b are LIVE on prod (946ca29, 2026-10-05).** 1b = bills API (`/clients/{id}/bills/` post/list/read/remove; Party exposes role+ledger; journal exposes entry_kind+bill; journal `correct` refuses vouchers with 409 wrong_entry_kind) and the web `Purchases & Sales` tab + voucher form + Day Book integration (route `/clients/$clientId/bills?bill=`). Not browser-tested by me (no login); covered by component tests, API tests and CI. Frontend gotchas: strict `noUncheckedIndexedAccess` (use `?.`/`??`), money fields are paise + `*_display`, validation errors come back under `fields` not `errors`, API tests cannot make requests as two firms in one test.

**Step 1c (built 2026-10-06, in CI):** bank rows on a party's account settle bills; a person decides every time (`ledger/settlement.py`: pure matcher `propose` + `validate`/`apply`/`settle_entry`/`party_line_of`; `approve(..., settlement=)`); auto_post, whole-band approval, learned rules and the AI model all stay away from party accounts; editing/removing a settled payment reopens bills (allocations deleted, recorded in the change log); API `classifications/{id}/settlement/`, `approvals` `settlements`, `journal-entries/{id}/settle/`; web `SettlementPanel`. **A 1a bug it exposed:** vouchers have NULL `source_transaction`, so `NOT IN (subquery)` in `classify.engine.unposted_in` returned nothing and one voucher emptied a client's review queue (fixed with `source_transaction__isnull=False`; regression test). Rule: any subquery used in `NOT IN`/`exclude(..__in=)` must be filtered to non-NULL.

**Step 1a (built):** `core/identity.py` (shared invoice key, same as GST's); `Party.ledger` FK (real FK, not name); voucher types Purchase/Sales/Debit Note/Credit Note; `JournalEntry.entry_kind`; `Bill` + `BillAllocation` with RLS, sign-off locks, never-UPDATE, same-client checks, allocation sums checked at commit (ledger/0012); `ledger/billing.py` (pure planner `plan_*` + posting + `allocate`/`apply_unapplied` + `party_position`); standard GST/RCM/cess/TDS-receivable/round-off ledgers; bank edit paths refuse voucher entries (`editing.require_bank_entry`). Planner tests run locally with no DB; DB tests only run in CI.

**Security lesson (found by the automated review):** a BEFORE trigger must never `set_config` the tenant from `NEW.firm_id` (it runs before the policy check, so the check would pass for any firm). Fixed in new triggers and repaired in ledger/0013 + classify/0020; `core/tests/test_trigger_tenant_switch.py` guards it by reading the catalogue (even a SQL comment containing the word trips it).

**Next:** 1d outstanding/party statement reports + open-items API/screen + the bypass reason (decision 8); 1e Tally openings/linking + OPENING bills; (1c done); (the 1b item is done; API schema regen: `python manage.py spectacular` then `node web/node_modules/openapi-typescript/bin/cli.js openapi.yaml -o src/api/schema.d.ts`, CI checks drift); 1c bank line settlement + matcher (party ledger first, a person confirms every settlement, edit/remove of bank entries must also delete allocations); 1d outstanding/party statement reports + open-items API + invoice CSV import; 1e Tally openings/linking + OPENING bills posting. Then stages 2-7 (invoice reading, matching, GST tie-in where gst/ register derives from bills, assets, payroll/TDS/cards, close screen). Known limits: detectors query per bill/line (aggregate before large clients); a bank EMI split into 3 lines will not mirror a 2-line loan instalment.
